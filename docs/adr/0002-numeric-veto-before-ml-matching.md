# กฎอ่านตัวเลขมาก่อน ML ในการจับคู่สินค้าซ้ำ

การจับคู่สินค้าซ้ำเดิมใช้ cosine similarity ของ embedding ล้วนๆ กับเกณฑ์ตายตัว 0.95/0.8 ซึ่งวัดแล้วว่าผิดอย่างน้อย 64% ในกลุ่มที่มันมั่นใจที่สุด — ที่คะแนน 0.993–0.998 คู่ที่เจอเป็นคนละ SKU ทุกคู่ (`หม้อหู - จระเข้ #22` ↔ `#28`, `ขวดซอส 7015` ↔ `7016`, `ถาดกลมเลส 32 cm` ↔ `34 cm`) เพราะ embedding ภาษาหลายภาษามอง `100g` กับ `150g` เกือบเหมือนกัน แต่ในร้านของใช้/ฮาร์ดแวร์ ตัวเลขนั่นคือสิ่งที่แยก SKU เราจึงวาง**กฎ deterministic ที่อ่านตัวเลขไว้หน้า pipeline ML** ไม่ใช่ปรับน้ำหนักโมเดลหรือเปลี่ยนไปใช้โมเดลที่ใหญ่กว่า

## Considered Options

- **ปรับเกณฑ์ cosine ให้สูงขึ้น** — ไม่ช่วย เพราะคู่ที่ผิดอยู่ที่ปลายสูงสุดของช่วงคะแนนอยู่แล้ว
- **เปลี่ยนไปใช้โมเดล System One (Jev / OpenThai-SystemOne)** — ยังคุ้มที่จะลอง แต่แก้ปัญหานี้ด้วยของที่ยังไม่ได้วัดกับข้อมูลไทยของเราคือการเดา และกฎตัวเลขจัดการได้ 81% ของคิวโดยไม่ต้องใช้ AI เลย
- **ขยายกฎให้ครอบคำบอกสี/ขนาด/รหัสรุ่นด้วย** — ปฏิเสธ เพราะไม่มีเกณฑ์เชิงกลไกใดแยก `ครีมอาบน้ำLux 80ml ม่วง` ↔ `ชมพู` (คนละของ) ออกจาก `ใบมีดโกน ดอลโก้` ↔ `ตอลโก้` (ของเดียวกัน พิมพ์ผิด) ได้ และการเริ่มทำคลังคำคุณลักษณะไม่มีจุดจบ

## ผลที่วัดได้ (2026-10-10)

วัดกับคู่ที่ผู้ใช้ตัดสินเอง 88 คู่ โดยปิดคำตอบของกฎและคะแนนความคล้ายไม่ให้เห็นระหว่างตัดสิน
และสลับลำดับคู่ เพื่อไม่ให้การตรวจลำเอียง:

| กิ่งของกฎ | ตรวจ | ผู้ใช้เห็นด้วย | เกณฑ์ | ผล |
|---|---|---|---|---|
| เลขไม่ตรงกัน (25 คู่ที่ embedding มั่นใจสูงสุด) | 25 | 25 (100%) | ≥95% | ผ่าน |
| ชื่อเหมือนเป๊ะหลังตัดเครื่องหมาย (ทั้งกลุ่ม) | 48 | 48 (100%) | 100% | ผ่าน |
| เลขฝั่งเดียว | 15 | 12 (80.0%) | ≥95% | **ไม่ผ่าน — ถอดออก** |

กิ่ง "เลขฝั่งเดียว" ถูกถอดออกจากกฎ เพราะความต่างของคำที่เหลือมักเป็นรหัสรุ่นหรือรหัสผู้ผลิต
ที่อีกฝั่งไม่ได้บันทึก ไม่ใช่สินค้าคนละตัว — `ขวดซอสใหญ่ (สีหวาน) 7026 BG` กับ
`ขวดซอสใหญ่(สีหวาน)` คือของชิ้นเดียวกัน กิ่งนี้จึงเงียบทั้งหมดและส่ง 96 คู่ให้คนตัดสิน

**เพดานของการจับคู่ด้วยข้อความ:** ในสามคู่ที่กฎวีโต้ผิด มีคู่หนึ่งที่ไม่มีกฎหรือโมเดลภาษาใด
จับได้เลย — `กล่องฝาปิด - สีใส 555 SMT` กับ `กล่องตะเกียบฝาใส` เป็นสินค้าชิ้นเดียวกัน
แต่ชื่อแทบไม่มีคำไหนตรงกัน (คะแนน embedding 0.745) แปลว่าในคลังนี้ SKU เดียวกันถูกบันทึก
ด้วยชื่อที่บรรยายของคนละแบบได้ การจับคู่จากชื่อสินค้าจึงมีเพดานที่ไม่ขึ้นกับคุณภาพของโมเดล
ทางออกของกรณีนี้คือบาร์โค้ด รหัสสินค้า หรือคน ไม่ใช่โมเดลที่เก่งขึ้น

**ผลสำมะโนของกิ่ง "เลขฝั่งเดียว" (11 ต.ค.):** ประชากรทั้งหมดของกิ่งนี้ในคิวสแกนคือ 97 คู่ และตอนนี้คนตัดสินครบทุกคู่
(15 จากรอบแรก + 82 จากรอบสอง) วีโต้ถูก 93 จาก 97 = 95.9% ผ่านเกณฑ์ 95% แบบฉิวเฉียด แต่**ไม่นำกลับมาเป็นกฎ**:
ส่วนที่ผิดคือของซ้ำจริง 4 คู่ (4.1%) ซึ่งถ้ากฎวีโต้ไป คู่นั้นจะถูกซ่อนจากการสแกนถาวร เพราะการสแกนข้ามคู่ที่กฎว่าคนละสินค้า
จึงไม่มีทางรู้ภายหลังว่ามีของซ้ำในสตอก ส่วนประโยชน์คือประหยัดการกด 97 ครั้งซึ่งทำไปแล้วครั้งเดียวจบ
ความเสียหายแบบเงียบกับประโยชน์แบบครั้งเดียวไม่คุ้มกัน
25/25 เป็นตัวอย่างจากคู่ที่ยากที่สุด จึงเป็น**ขอบล่าง** (ความแม่นจริงเหนือราว 86-89%
อย่างมั่นใจ) ไม่ใช่ 100% ทั้งกอง ส่วน 48/48 ดูครบทั้งกลุ่มจึงไม่มีความไม่แน่นอน
ผลทั้งหมดแช่แข็งไว้ที่ `tests/fixtures/dedup_human_labels_v1.json`

## Consequences

- กฎนี้**พูดได้สองอย่างเท่านั้น**: "คนละสินค้า" เมื่อตัวเลขไม่ตรง และ "สินค้าซ้ำ" เมื่อชื่อเหมือนกันเป๊ะหลังตัดเครื่องหมาย เมื่อตัวเลขตรงกันแต่คำต่างกัน มันต้องเงียบ — ห้ามเดาว่าซ้ำ
- ผลของกฎ**ห้ามเขียนลงช่อง `reviewed`** ไม่ว่าจะมั่นใจแค่ไหน คำนั้นสงวนให้คนเท่านั้น (ดู CONTEXT.md) การที่เครื่องประทับ `reviewed=true` ให้ตัวเองคือสาเหตุที่ข้อมูลผิด 1,344 แถวซ่อนตัวอยู่ได้นานและถูกใช้สอน ML
- ราคาในชื่อนับเป็นตัวระบุรายการ ยกเว้นรูปแบบ `(ราคา 25 บาท)` ซึ่งเป็นหมายเหตุ — เป็นข้อยกเว้นที่มาจากข้อมูลจริง ไม่ใช่การออกแบบล่วงหน้า
- กฎถูกวางไว้ใน `is_pair_resolved` ของ `src/api/routers/internal_match.py` ซึ่งเรียกจากสามจุดในลูปสแกน (เดิมทั้งสามจุดคัดออกเฉพาะ `reviewed=true` คัดลอกเงื่อนไขไว้คนละที่) การสแกนครั้งต่อไปจึงไม่ยื่นคู่ที่ตัวเลขไม่ตรงให้คนดูอีก
- **ใช้กับเส้นทาง import แล้ว** (`/import-dedup` ซึ่งเป็นเส้นเดียวที่ wizard เรียก) backend ติด `identityVerdict` ให้ทุกคู่ที่จับคู่ได้ (`annotate_identity`) แล้ว frontend ใช้ใน `classifyDedupBucket`: คะแนน ≥0.95 ทิ้งได้ต่อเมื่อกฎยืนยันว่าซ้ำ · กฎว่าคนละสินค้า → "ของใหม่" ทุกช่วงคะแนน · นอกนั้นส่งให้คน ตัวเลขที่ทำให้เปลี่ยน: ไฟล์ทดสอบ 405 รายการเคยทิ้งอัตโนมัติ 37 รายการ กฎเห็นด้วย 26 · **ไม่เห็นด้วย 3** (`เก้าอี้เตี้ย 366`≠`555`, `กะละมัง 004 58`≠`004/53`, `กล่องแช่4401`≠`4402`) · เงียบ 8 และในคิวก้ำกึ่ง 147 รายการ กฎว่าคนละสินค้า 77 รายการ
- การทิ้งสินค้านำเข้าไม่เหมือนการตัดสินอื่น: "ของใหม่" ยังมีคนยืนยันหมวดต่ออีกด่าน แต่ "มีในสตอกแล้ว" ไม่มีใครเห็นอีกเลย กฎที่ผิดฝั่งแรกจึงเสียหายน้อยกว่าฝั่งหลังมาก นโยบายถึงเข้มฝั่งทิ้งและหลวมฝั่งนับเป็นของใหม่
- **`/file-dedup` (`deduplicate_files`) ไม่ได้แก้**: ผู้เรียกเดียวคือ Edge Function `product-deduplication` ซึ่งแตะล่าสุด 26 มิ.ย. ไม่อยู่ใน `supabase/config.toml` และฝัง `http://127.0.0.1:8000` ซึ่งใน runtime ของ Edge Function ชี้กลับเครื่องของตัวมันเอง ไม่ใช่ FastAPI บนเครื่อง จึงน่าจะใช้งานไม่ได้อยู่แล้ว
