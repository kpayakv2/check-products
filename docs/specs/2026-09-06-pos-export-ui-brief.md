## 1. สิ่งที่ต้องออกแบบ

แท็บที่ 5 ของหน้า `/data-quality` ชื่อ **"ส่งออก POS"** ต่อจาก
เช็คข้อมูลซ้ำ → ตรวจสอบหมวดหมู่ → ตรวจซ้ำของเก่า → ระบบเรียนรู้ AI

ไฟล์: `taxonomy-app/components/data-quality/PosExportTab.tsx`

## 2. บริบท — ใครใช้ ใช้ตอนไหน

ร้านค้าปลีกไทย พนักงานออฟฟิศ 2–3 คนใช้เครื่องเดียวกันในออฟฟิศ ปลดล็อกด้วยรหัสผ่านชุดเดียว
(ไม่มีระบบ login รายคน) เปิดบนเดสก์ท็อปเป็นหลัก แต่มีเปิดบนแท็บเล็ต/มือถือบ้าง

**งานที่ทำอยู่ก่อนหน้า:** เอารายการสินค้าที่สั่งเข้ามาใหม่ มาเทียบกับสตอกเดิม 3,103 รายการ
เพื่อหาว่าตัวไหน "ยังไม่เคยมีในร้าน" ผ่าน 3 แท็บแรกไปแล้ว

**งานในแท็บนี้:** เอาผลลัพธ์นั้น (ตอนนี้ 221 รายการ) ออกมาเป็นไฟล์ `.txt` แล้วเอาไปนำเข้า POS

## 3. โจทย์ที่แท้จริง — ทำไมหน้านี้ไม่ใช่แค่ "ปุ่มดาวน์โหลด"

การกดปุ่มนี้ทำ 3 อย่างพร้อมกัน และ **ย้อนกลับยาก**

1. **ออกรหัสสินค้าถาวร** — สินค้า 221 รายการที่ยังไม่มีรหัส จะได้รหัสใหม่ (`HH696`, `KIT414` …)
   เขียนลงฐานข้อมูลทันที รหัสนี้จะไปอยู่ใน POS ต่อ แก้ทีหลังต้องแก้สองฝั่ง
2. **ล้างคิว** — ทั้ง 221 รายการถูกตีว่า "ส่งออกแล้ว" หายจากหน้านี้ กดอีกทีจะไม่เจอ
3. **ไฟล์อาจถูก POS ปฏิเสธ** — POS บังคับ 6 ช่อง ตอนนี้ **ราคาว่างทั้ง 221 แถว**

> ⚠️ นี่คือแกนของงานออกแบบ: **ทำให้คนเห็นผลลัพธ์ทั้งสามข้อก่อนกด โดยไม่ทำให้กดไม่ลง**
> เจ้าของงานรู้เรื่องราคาว่างแล้วและตั้งใจจะโหลดอยู่ดี ดีไซน์ต้องเตือนให้ชัด แต่ไม่ขวาง

## 4. สถานะที่ต้องออกแบบ (5 สถานะ)

| สถานะ | เกิดเมื่อ | ต้องสื่ออะไร |
|---|---|---|
| **กำลังโหลด** | เปิดแท็บครั้งแรก | รอสักครู่ ไม่ต้องหวือหวา |
| **ไม่มีของรอส่ง** | `total = 0` | ไม่ใช่ error — เป็นข่าวดี ทำงานครบแล้ว · ปุ่มโหลดต้องปิด |
| **พร้อม แต่ยังขาดช่องบังคับ** | มีของ + `issues` ไม่เป็นศูนย์ | ← **สถานะจริงตอนนี้** ออกแบบให้ดีที่สุด |
| **พร้อมครบ** | มีของ + ไม่ขาดช่องไหน | มั่นใจได้ กดได้เลย |
| **โหลดสำเร็จแล้ว** | หลังกดปุ่ม | ต้องมีจังหวะยืนยัน — รายการเพิ่งหายไป 221 รายการ ถ้าหน้าว่างเปล่าเฉย ๆ คนจะงงว่าพังหรือสำเร็จ |

**สถานะที่ 5 คือจุดที่ดีไซน์เดิมยังไม่มีคำตอบ** — แท็บอื่นในแอปไม่มีงานที่ "ทำเสร็จแล้วของหายไปทั้งชุด"

## 5. ข้อมูลที่มีให้แสดง

จาก `GET /api/pos-export`:

```ts
{
  total: number            // 221
  issues: {                // นับ "จำนวนแถวที่ขาด" ต่อช่องบังคับ
    missingItemId: number
    missingBarcode: number
    missingItemName: number
    missingUnitName: number
    missingItemGroup: number
    missingPrice: number   // ตอนนี้ = 221 ที่เหลือ = 0
  }
  preview: Array<{         // สูงสุด 50 แถว
    itemGroup: string      // "ของใช้ในบ้าน"
    subGroup1: string      // "ตะกร้า/กระจาด"
    subGroup2: string      // ว่างเสมอในตอนนี้
    itemId: string         // "HH696"
    barcode: string        // ปกติเท่ากับ itemId
    itemName: string       // ชื่อไทยยาว ๆ
    unitName: string       // "ชิ้น"
    price: number | null   // null ทั้งหมดในตอนนี้
    vat: string            // "V"
  }>
}
```

**หมายเหตุสำคัญ:** `preview` แสดงแค่ 50 แถวแรก แต่ไฟล์จริงมี 221 แถว — ต้องสื่อความต่างนี้ให้ชัด
ไม่ให้คนเข้าใจว่าไฟล์มีแค่ 50

## 6. การกระทำบนหน้าจอ

| ปุ่ม | ทำอะไร | ข้อควรระวังด้านดีไซน์ |
|---|---|---|
| **ดาวน์โหลด .txt** | สร้างไฟล์ + เขียนรหัส + ล้างคิว | ปุ่มหลัก · ต้องปิดเมื่อ `total = 0` · ต้องมีสถานะ "กำลังสร้างไฟล์..." เพราะยิง DB 221 รายการ ใช้เวลาหลายวินาที |
| **รีเฟรช** | โหลดตัวเลขใหม่ | ปุ่มรอง อย่าให้เด่นแข่งกับปุ่มหลัก |

**ยังไม่ต้องออกแบบ:** การกรอกราคา/หน่วยรายตัว — อยู่นอกขอบเขตรอบนี้ ([ดูสเปก](2026-09-06-pos-export.md) หัวข้อ "นอกขอบเขต")

## 8. ข้อบังคับทางเทคนิค (ห้ามพลาด)

**`data-testid` เหล่านี้ต้องมีครบ** — Playwright กับ Jest ผูกไว้แล้ว เปลี่ยนชื่อเมื่อไหร่เทสต์แดง

```
pos-export-tab        ราก
tab-pos-export        ปุ่มแท็บ (อยู่ในหน้า data-quality/page.tsx)
pos-export-loading    สถานะกำลังโหลด
pos-export-total      ตัวเลขยอดรวม
pos-export-warning    กล่องเตือนช่องที่ขาด
pos-export-download   ปุ่มดาวน์โหลด
pos-export-empty      สถานะไม่มีของ
pos-export-row-0..n   แถวในตัวอย่าง
```

**อื่น ๆ**

- **ห้ามให้หน้าเลื่อนแนวนอนที่จอ 375px** — มีเทสต์ e2e ตรวจข้อนี้โดยตรง
  ตารางที่กว้างต้องเลื่อนในกรอบตัวเอง (`overflow-x-auto`) ไม่ใช่ดันทั้งหน้า
- **ข้อความไทยต้องไม่ถูกตัดสระบน/ล่าง** — `line-height` ต่ำเกินไปทำสระหายบ่อยในแอปนี้
  ชื่อสินค้าจริงยาวได้ถึง ~60 ตัวอักษร เช่น
  `ตะหลิวยาว4" ด้ามดำ fw 038 ม้าน้ำ`, `กะละมังเหลี่ยม 666 OS`,
  `เก้าอี้ซักผ้ากลม 9025 สีหวาน AB V-NICE`
  ชื่อหมวดก็ยาว: `ผลิตภัณฑ์ทำความสะอาดในบ้าน`, `อุปกรณ์ประกอบอาหาร/ตะแกรงครัว`
- **Tailwind ใช้ได้เฉพาะใน `taxonomy-app/`** และห้ามใช้ `any` ใน TypeScript
- ปุ่มดาวน์โหลดต้องกันกดซ้ำระหว่างกำลังทำงาน — กดสองครั้ง = ออกรหัสสองชุด

## 9. โครงข้อมูลที่ต้องสื่อ (ไม่ใช่การจัดวาง — จัดวางเป็นงานของดีไซเนอร์)

เรียงตามลำดับความสำคัญ

1. **จำนวนที่รอส่งออก** — ตัวเลขใหญ่ อ่านปราดเดียวรู้
2. **ความพร้อมของไฟล์** — 6 ช่องบังคับ ช่องไหนครบ ช่องไหนขาด ขาดกี่แถว
   (ตอนนี้ 5 ครบ 1 ขาด — ดีไซน์ควรทำให้ "เกือบพร้อม" อ่านออกทันที ไม่ใช่เห็นเป็นแค่ error ก้อนเดียว)
3. **ผลของการกดปุ่ม** — จะออกรหัสถาวรและล้างคิว
4. **ตัวอย่างข้อมูล** — ให้เชื่อมั่นว่าไฟล์ถูกต้อง พร้อมบอกว่าเห็นแค่ 50 จาก 221
5. **ปุ่มดาวน์โหลด**

## 10. คำถามที่อยากให้ดีไซน์ตอบ

1. **จะแสดงความพร้อม 6 ช่องยังไงให้อ่านปราดเดียว** โดยไม่กลายเป็นตารางน่าเบื่อ
   หรือกล่องเตือนสีแดงที่คนเลิกอ่านหลังเห็นครั้งที่สาม
2. **จะสื่อ "กดแล้วย้อนไม่ได้" ตรงไหน** — ข้อความใต้ปุ่ม? เปลี่ยนคำบนปุ่ม? กล่องยืนยันอีกชั้น?
   (ถ้าเสนอกล่องยืนยัน ต้องคิดเผื่อคนที่ต้องกดทุกสัปดาห์ด้วย)
3. **หลังโหลดเสร็จหน้าตาเป็นยังไง** — รายการหายไป 221 รายการทันที
   ต้องมีอะไรบอกว่าสำเร็จ และบอกว่าต่อไปทำอะไร (เอาไฟล์ไปนำเข้า POS)
4. **ตัวอย่างข้อมูลบนมือถือ** — 9 คอลัมน์ใส่จอ 375px ไม่ได้ จะเลื่อนแนวนอน ยุบเป็นการ์ด
   หรือเลือกแสดงแค่บางคอลัมน์

## 11. สิ่งที่อยากได้กลับมา

- โครงหน้าจอทั้ง **5 สถานะ** ในข้อ 4
- เดสก์ท็อป + มือถือ (375px)
- ระบุสี/ระยะ/ขนาดฟอนต์เป็นคลาส Tailwind ที่ใช้ได้จริง ไม่ใช่ค่ากลาง ๆ
- ถ้าเสนอองค์ประกอบที่แอปยังไม่มี (เช่น กล่องยืนยัน) ให้บอกด้วยว่าอิงแพตเทิร์นไหนในแอป

## 12. นอกขอบเขตบรีฟนี้

- ฟอร์มกรอกราคา/หน่วยรายตัว
- แก้ดีไซน์ 4 แท็บเดิม
- โหมดมืด (แอปมีแต่ light mode)
- ระบบ login รายคน (ไม่มีในโปรเจกต์นี้ และไม่ได้จะทำ)
