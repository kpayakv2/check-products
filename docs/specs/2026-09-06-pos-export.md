# สเปก: ส่งออกไฟล์นำเข้าสินค้าเข้า POS (2026-09-06)

**สถานะ:** ตกลงกับเจ้าของงานแล้ว รอลงมือ
**แผนที่ทำตามสเปกนี้:** [docs/superpowers/plans/2026-09-06-pos-export.md](../superpowers/plans/2026-09-06-pos-export.md)

## ที่มา

เจ้าของร้านมีไฟล์ต้นแบบที่ POS กินได้อยู่แล้ว สร้างจาก `excel_to_txt_gui.exe`
(ที่ `D:\OneDrive\เอกสาร\pos\POSไฟล์นำเข้า\นำเข้าสินค้า\`) ซึ่งกรอง `ImportItem.xlsx`
ตามชื่อสินค้าที่เลือกจาก dropdown แล้วเขียน `.txt` ออกมา

ระบบ check-products หาสินค้าใหม่ที่ยังไม่มีในสตอกได้แล้ว แต่ยังไม่มีทางส่งผลลัพธ์
เข้า POS — ต้องคัดลอกมือ งานนี้ปิดช่องว่างนั้น

ไฟล์ต้นแบบที่ใช้ถอดสเปก: `รองเท้าขัดมันหญิงแชปปี้.txt` (34 แถว) เทียบกับพี่น้องอีก
4 ไฟล์ในโฟลเดอร์เดียวกัน — หัวตารางตรงกันทั้งหมด

## รูปแบบไฟล์ (ยืนยันจากไบต์จริง)

| คุณสมบัติ | ค่า |
|---|---|
| ตัวคั่น | Tab (`\t`) |
| จำนวนคอลัมน์ | 9 |
| เข้ารหัส | UTF-8 **ไม่มี BOM** |
| ขึ้นบรรทัด | CRLF (`\r\n`) รวมบรรทัดสุดท้าย |
| เครื่องหมายคำพูด | **ไม่มีเลย** — นับ `"` ในไฟล์ต้นแบบได้ 0 ตัว |
| แถวแรก | หัวตาราง |

### หัวตาราง — ต้องตรงตัวอักษร

```
Item Group(ชื่อกลุ่มสินค้า)	Sub Group1(ชื่อกลุ่มย่อย1)	Item ID(รหัสสินค้า)	Barcode(บาร์โค้ด)	Item Name(ชื่่อสินค้า)	Unit Name(ชื่อหน่วย)	Price(ราคาขาย)	Vat	Sub Group2
```

> ⚠️ **คอลัมน์ที่ 5 สะกดผิดในต้นฉบับ และห้ามแก้**
> `Item Name(ชื่่อสินค้า)` มีไม้เอก (U+0E48) **ซ้ำสองตัว** ต่อจากสระอือ
> ลำดับจริง: `U+0E0A U+0E37 U+0E48 U+0E48 U+0E2D U+0E2A U+0E34 U+0E19 U+0E04 U+0E49 U+0E32`
>
> สคริปต์เดิม `excel_to_txt_gui.py` จับคอลัมน์ด้วยสตริงนี้เป๊ะ ๆ
> (`df["Item Name(ชื่่อสินค้า)"]`) และไฟล์บันทึกข้อจำกัดข้าง ๆ ก็ย้ำว่า
> "คอลัมน์ต้องตรงตามชื่อ" ถ้ามีใครไป "แก้คำผิด" ให้ ไฟล์จะใช้กับ POS ไม่ได้
>
> **ในโค้ดให้เขียนด้วย escape (`\u0E48\u0E48`) ไม่ใช่ตัวอักษรตรง ๆ** — ไม้เอกซ้อนกัน
> มองด้วยตาแทบไม่เห็น เผลอโดน formatter หรือ IDE จัดให้เมื่อไหร่ก็พังเงียบ ๆ
> อีก 8 คอลัมน์สะกดปกติ ตรวจ codepoint แล้ว

## ข้อกำหนดฝั่ง POS (จากคู่มือ Import External Data)

หน้าจับคู่คอลัมน์ของ POS มีปลายทางให้เลือก **8 ช่อง**

**บังคับ 6 ช่อง — ขาดช่องไหน POS ไม่รับไฟล์**

| ปลายทางใน POS | ความหมาย | ระบบเรามีข้อมูลไหม |
|---|---|---|
| `Item ID` | รหัสสินค้า | ❌ ว่างทั้ง 221 |
| `Barcode` | บาร์โค้ด | ⚠️ กู้ได้ 203/405 จากไฟล์ต้นทาง |
| `Item Name` | ชื่อสินค้า | ✅ ครบ |
| `Price` | ราคาขาย | ⚠️ กู้ได้ 303/405 จากไฟล์ต้นทาง |
| `Unit Name` | ชื่อหน่วย | ❌ ไม่มีเลย และกู้ไม่ได้ |
| `Item Group` | ชื่อกลุ่มสินค้า | ✅ ครบ (จาก taxonomy) |

**ทางเลือกอีก 2 ช่อง**

| ปลายทาง | ความหมาย |
|---|---|
| `ภาษี` | `N` = เว้นภาษี · `V` = คิดภาษี — ไฟล์ต้นแบบเป็น `V` ทุกแถว |
| `รูปแบบสถานะสินค้า` | `0` สินค้าขายได้ · `1` วัตถุดิบขายได้ · `2` สินค้าระหว่างประกอบขายได้ · `3` สินค้าขายไม่ได้ · `4` วัตถุดิบขายไม่ได้ · `5` สินค้าระหว่างประกอบขายไม่ได้ |

### สองข้อสังเกตจากคู่มือ

**1. `Sub Group1` และ `Sub Group2` ไม่มีปลายทางให้ map** — POS มีช่องกลุ่มสินค้าช่องเดียวคือ
`Item Group` แต่ไฟล์ต้นแบบมี 9 คอลัมน์และ POS เคยรับมาแล้ว แปลว่าคอลัมน์ที่ map ไม่ได้
จะถูกข้ามไปเฉย ๆ ไม่ทำให้ไฟล์เสีย **จึงคงไว้ทั้ง 9 คอลัมน์ตามต้นแบบ** — ไฟล์ที่พิสูจน์แล้วว่า
ใช้ได้ ปลอดภัยกว่าไฟล์ที่ตัดคอลัมน์ออกเองแล้วเดาว่าน่าจะยังใช้ได้

**2. `รูปแบบสถานะสินค้า` ไม่มีในไฟล์ต้นแบบ** — เป็นช่องทางเลือก และไฟล์ที่ POS เคยรับก็ไม่มี
จึงไม่ใส่ ถ้าวันหลังต้องใช้ ค่อยเพิ่มเป็นคอลัมน์ที่ 10 พร้อมคอลัมน์ `product_status_type`
ในตาราง (default `0` = สินค้าขายได้)

## การ map หมวดหมู่

`taxonomy_nodes` มี `parent_id` และ `level` — ปัจจุบันมีแค่ 2 ชั้น (16 + 118 โหนด)
แต่โครงสร้างรองรับลึกกว่านั้นได้

ไล่สายจาก `products.category_id` ขึ้นไปหาราก แล้ววางตามความลึก:

| ความลึก | คอลัมน์ POS |
|---|---|
| ราก (ชั้น 1) | `Item Group` |
| ชั้น 2 | `Sub Group1` |
| ชั้น 3 | `Sub Group2` |
| ลึกกว่านั้น | ทิ้ง |

วันไหนเพิ่ม taxonomy ชั้น 3 เข้ามา `Sub Group2` จะเติมเองโดยไม่ต้องแก้โค้ด

**ทำใน TypeScript ไม่ใช่ SQL** — AGENTS.md ห้าม raw SQL ในโค้ดแอป และ taxonomy
มีแค่ 134 โหนด ดึงมาทั้งก้อนแล้วไล่สายในหน่วยความจำถูกกว่าเขียน recursive CTE

**ชื่อหมวดมี `_` คั่นอยู่ 59 จาก 221 รายการ** (`เครื่องเขียน_สำนักงาน`,
`เครื่องมือ_ฮาร์ดแวร์`) — แทนด้วยช่องว่างตอนเขียนไฟล์ ไม่แก้ในฐานข้อมูล
เพราะชื่อพวกนี้ผูกกับ `keyword_rules` ที่ mine ไว้

**เคสขอบ:** มี 1 รายการที่ `category_id` ไม่ได้ชี้โหนดชั้น 2 — สายที่ได้จะมีโหนดเดียว
`Item Group` ได้ชื่อนั้น ส่วน `Sub Group1`/`Sub Group2` ว่าง ไม่ crash

POS บังคับ 6 ช่อง ตอนนี้เติมได้ครบ 2 ช่อง ไฟล์ที่ส่งออกวันนี้ POS **ยังไม่รับ**

ไฟล์ต้นทางที่นำเข้าเมื่อ 27 ส.ค. ยังอยู่ในรีโป —
`input/new_product/POS_เพิ่มสินค้า_20250727_063658_จากไฟล์สินค้าใหม่.csv`
(405 แถว, UTF-8 มี BOM, 10 คอลัมน์) เปิดดูแล้วพบว่ามีข้อมูลที่ตอนนำเข้าไม่ได้ map ไว้

| `Barcode` | **203 / 405** | → `Barcode` ✅ EAN 13 หลัก |
| `รายการ` | 405 | ชื่อสินค้า — ใช้จับคู่กับ `products.name_th` |
| `หน่วย` | 388 | ❌ **เป็นตัวเลข** (12.0, 1.0, 195) = จำนวนต่อแพ็ก ไม่ใช่ชื่อหน่วย |

### การจับคู่กลับไปหาไฟล์ต้นทาง — ทดสอบแล้วได้ 100% (ยังไม่ทำ)

> **สถานะ: ไม่อยู่ในขอบเขตงานนี้** ตกลงกันว่าไป map คอลัมน์ตอน import รอบหน้าแทน
> บันทึกผลการทดสอบไว้เพราะถ้าวันหลังอยากเติมราคาย้อนหลังจริง ๆ วิธีที่ใช้ได้อยู่ตรงนี้แล้ว
> ไม่ต้องมาสำรวจใหม่

ตอนนำเข้า ชื่อสินค้าถูกทำความสะอาด (ตัวพิมพ์เล็ก + ตัดวรรคตอน) ชื่อใน `products.name_th`
จึงไม่ตรงกับคอลัมน์ `รายการ` ในไฟล์ต้นทางแบบตัวต่อตัว
(`ไม้แขวนเสื้อ - ลวด 111 หนุมาน STCP` → `ไม้แขวนเสื้อ ลวด 111 หนุมาน stcp`)
และ `metadata.clean_name` ก็เท่ากับ `name_th` ทุกแถว ใช้ช่วยไม่ได้

ทดลองจับคู่ 3 ระดับกับข้อมูลจริง:

| การ normalize | จับคู่ได้ | คลุมเครือ |
|---|---|---|
| ตัวพิมพ์เล็ก + ยุบช่องว่าง | 102 / 405 | 0 |
| **+ แทนวรรคตอนด้วยช่องว่าง** | **405 / 405** | **0** ✅ |
| + ตัดตัวคั่นออกทั้งหมด | 405 / 405 | 6 ⚠️ |

**ระดับกลางคือคำตอบ** — จับคู่ครบทุกแถวโดยไม่มีคู่ไหนกำกวมเลย ระดับที่แรงกว่านั้น
เริ่มมีสินค้าคนละตัวชนกัน 6 คู่ จึงแย่กว่า ไม่ใช่ดีกว่า

```
lower() → แทนทุกอักขระที่ไม่ใช่ตัวอักษร/ตัวเลข/ไทย/" ด้วยช่องว่าง → ยุบช่องว่าง → trim
```

เติมกลับได้จริงใน 221 รายการ: **ราคา 171 แถว · บาร์โค้ด 131 แถว** (ได้ทั้งคู่ 127 · ไม่ได้เลย 46)

### รหัสสินค้า — สตอกเดิมมีระบบอยู่แล้ว

สตอก 3,103 รายการใช้รูปแบบ `<PREFIX><เลขรัน>` และ **prefix ผูกกับหมวดหลักแบบ 1:1**
15 จาก 16 หมวดใช้ prefix เดียว 100% (เครื่องครัว 99.8% มีหลุด 1 รายการ)
เลขรันเดินต่อเนื่องไม่มีช่องว่าง — จำนวนแถวเท่ากับเลขสูงสุดพอดีทุก prefix

| หมวดหลัก | prefix | ใช้แล้วถึง | หมวดหลัก | prefix | ใช้แล้วถึง |
|---|---|---|---|---|---|
| ผลิตภัณฑ์ดูแลส่วนบุคคล | `PC` | 754 | อุปกรณ์ทำความสะอาด | `CL` | 114 |
| ของใช้ในบ้าน | `HH` | 695 | ของเล่น_นันทนาการ | `TOY` | 65 |

รหัสใหม่จึงออกให้อัตโนมัติได้ — ดูหมวดหลักที่ AI จัดให้ แล้วเดินเลขต่อจากตัวสูงสุด
เช่นสินค้าใหม่ในของใช้ในบ้านได้ `HH696`, `HH697`, … เข้าชุดกับสตอกเดิมทันที

**ทั้ง 221 รายการตกอยู่ใน 13 หมวดหลัก ซึ่งมี prefix ครบทุกหมวด** — ไม่มีรายการไหนหาที่ลงไม่ได้
(ของใช้ในบ้าน 76 · เครื่องครัว 47 · เครื่องมือ 25 · เครื่องเขียน 23 · ดูแลส่วนบุคคล 15 ·
เบ็ดเตล็ด 14 · ทำความสะอาด 8 · ที่เหลืออีก 6 หมวด รวม 13)

#### กติกาการออกรหัส

1. หาหมวดหลัก (รากของสายหมวดหมู่) ของสินค้า
2. เปิดตาราง prefix — **ตารางคงที่ในโค้ด ไม่ derive จากข้อมูลตอนรัน** เพราะหมวดที่ยังไม่มี
   สินค้าเก่าเลยจะหา prefix ไม่เจอ หมวดที่ไม่อยู่ในตารางตกไปใช้ `MIS`
3. หาเลขสูงสุดที่ใช้ไปแล้วของ prefix นั้นจากทั้งตาราง `products`
4. ไล่แจกเลขถัดไปเรียงตามชื่อสินค้า เพื่อให้ผลซ้ำเดิมได้ถ้ารันใหม่

**เขียนลง `products.sku` ตอนกดดาวน์โหลด ไม่ใช่สร้างลอย ๆ ตอนประกอบไฟล์** — รหัสที่ส่งเข้า
POS ต้องนิ่งตลอดไป ถ้าสร้างใหม่ทุกครั้งที่ export สินค้าตัวเดียวกันจะได้คนละรหัสในแต่ละรอบ

`products.sku` มี `UNIQUE` constraint (`products_sku_key`) อยู่แล้ว ฐานข้อมูลจะกันรหัสชนให้
ตัวจัดรหัสยังต้องคำนวณเลขสูงสุดใหม่ทุกครั้งที่แจก ไม่ใช้ค่าที่แคชไว้

### ชื่อหน่วย

ไม่มีข้อมูลหน่วยขายในระบบเลย และไฟล์ต้นทางก็ไม่มี (`หน่วย` เป็นจำนวนต่อแพ็ก ส่วน `จำนวน`
เป็นหน่วยซื้อ) แต่ POS บังคับช่องนี้ จึงใส่ค่าเริ่มต้น **`ชิ้น`** ทุกแถว แล้วไปแก้ตัวที่ผิดใน POS

`unit_name` ในฐานข้อมูลเป็น **nullable ไม่มี default** ส่วนค่า `ชิ้น` เติมตอนประกอบไฟล์
— ฐานข้อมูลไม่ควรอ้างว่ารู้หน่วยของสินค้า 3,103 รายการเก่าทั้งที่ไม่เคยมีใครกรอก
วันไหนกรอกหน่วยจริงเข้ามา ค่าในฐานข้อมูลจะชนะค่าเริ่มต้นเอง

### สรุปต่อช่องบังคับ (ตามที่ตัดสินใจแล้ว)

| ช่อง | ตอนนี้ | เมื่องานนี้เสร็จ | มาจากไหน |
|---|---|---|---|
| `Item Name` | ✅ 221 | ✅ **221** | `products.name_th` |
| `Item Group` | ✅ 221 | ✅ **221** | หมวดหลักจาก taxonomy |
| `Item ID` | ❌ 0 | ✅ **221** | ออกอัตโนมัติจาก prefix หมวด |
| `Barcode` | ❌ 0 | ✅ **221** | ไม่มีของจริง → ใช้ `Item ID` ซ้ำตามไฟล์ต้นแบบ |
| `Unit Name` | ❌ 0 | ✅ **221** | ค่าเริ่มต้น `ชิ้น` |
| `Price` | ❌ 0 | ❌ **0** | ⚠️ ยังว่าง — ดูข้างล่าง |

**`Price` จะยังว่างทั้ง 221 แถว** ตกลงกันว่าไม่ backfill แต่ไป map คอลัมน์ตอน import รอบหน้า

ข้อควรรู้: สินค้า 221 รายการนี้อยู่ในฐานข้อมูลแล้ว การนำเข้าไฟล์เดิมซ้ำจะถูกตัวตรวจซ้ำ
จับได้และตีเป็น duplicate ราคาของ **ชุดนี้** จึงไม่ได้ถูกเติมจากการ import รอบหน้าโดยอัตโนมัติ
— รอบหน้าที่ map ราคาไว้จะช่วย**ของล็อตใหม่**ที่ยังไม่เคยเข้าระบบ ถ้าอยากได้ราคาของ 221
รายการนี้ด้วย ต้องเติมทางอื่น (สคริปต์ backfill ที่ทดสอบไว้แล้วด้านบน หรือกรอกใน POS หลังนำเข้า)

ตัวส่งออกจะ **แสดงจำนวนแถวที่ยังไม่มีราคาก่อนกดโหลด** แต่ไม่บล็อกการดาวน์โหลด

ท่อนำเข้ารองรับทั้ง `sku` และ `price` อยู่แล้ว —

### ผลต่อการออกแบบ

ตัวส่งออกต้อง **นับและแสดงแถวที่ขาดช่องบังคับทั้ง 6 ก่อนกดโหลด** ไม่ใช่แค่ `Item ID`/`Price`
และควรกันไม่ให้โหลดไฟล์ที่ POS จะปฏิเสธแน่ ๆ ออกไปโดยไม่รู้ตัว

## นอกขอบเขต

- แตกไซซ์/สี (`SS-CHP-CB999-BK-34`) — ระบบไม่มีข้อมูลชั้นนี้ ต้องทำเป็นงานแยก
- แก้ `status` ที่พลิกเป็น `approved` ตอน verify — เลี่ยงด้วย `metadata.source` แทน
- **เติมราคา/บาร์โค้ดย้อนหลังให้ 221 รายการ** — วิธีทดสอบไว้แล้ว (จับคู่ได้ 405/405) แต่ตกลงว่าไม่ทำรอบนี้
- คอลัมน์ `รูปแบบสถานะสินค้า` (0–5) — เป็นช่องทางเลือกของ POS และไฟล์ต้นแบบไม่มี
- แก้ชื่อหน่วยรายตัว — ใส่ `ชิ้น` ทุกแถวก่อน แล้วไปแก้ใน POS
- หน้าจอกรอกราคา/หน่วยในเว็บ — ถ้าวันหลังอยากได้ ต้องทำเป็นงานแยก
