# 03: ปุ่ม resolve สร้างแถวซ้อนเมื่อทิศทางคู่ (A,B) ต่างจากแถวเดิม

**Labels:** `bug`
**Parent:** [แผนที่](../map.md)
**Blocked by:** —
**Assignee:** —
**Status:** open — ตกลงแบบกับผู้ใช้ครบแล้ว (grilling 2026-10-11) ยังไม่ลงมือ ดูหัวข้อ "คำตัดสิน" ท้ายไฟล์

## ปัญหา

`taxonomy-app/app/api/similarity/resolve/route.ts` บันทึกคำตัดสินด้วย `upsert(..., { onConflict: 'product_a_id, product_b_id' })` ซึ่งไวต่อทิศทาง: คู่ (A,B) กับ (B,A) ถือเป็นคนละคีย์ (constraint `UNIQUE (product_a_id, product_b_id)`) ถ้าแถวในตารางกับแถวที่ route เขียนมีทิศต่างกัน จะ **สร้างแถวใหม่** และแถวเดิมค้าง `reviewed=false`

**สาเหตุจริง (แก้ 2026-10-11 หลังตรวจ DB — ฉบับแรกของตั๋วนี้เขียนผิดว่า "หน้าจอส่ง (B,A) มา"):** route **เรียงไอดีอยู่แล้ว** (`[id_a, id_b].sort()`) ทิศที่หน้าจอส่งมาจึงไม่มีผล ปัญหาอยู่ที่ **แถวเดิมไม่ได้เรียง** — `scripts/build_similarity_training_data.py` เขียนแถว `legacy_embedding_scan` ตามลำดับที่สแกนเจอ ไม่เรียงไอดี (698 แถวที่ยังไม่ตรวจ และ 188 แถวที่ตรวจแล้ว มี `product_a_id > product_b_id`; `import_wizard_dedup` ก็มีอีก 52 แถว) ส่วนแถว `cosine` ทั้ง 104 แถวที่ route เขียนเรียงแล้วทุกแถว ครบทั้ง 31 คู่ที่ซ้อนเป็นแบบเดียวกันหมด: แถว `cosine` ที่เรียงแล้วและคนตัดสินแล้ว (merge 25 · keep_both 6) + แถว `legacy_embedding_scan` ที่ยังไม่เรียงและยังไม่ตรวจ

ผลข้างเคียงอีกข้อ: เมื่อทิศตรงกัน upsert จะเขียน `algorithm='cosine'`/`match_type='semantic'` ทับลงแถวเดิม ทำให้เสียร่องรอยว่าคู่นั้นมาจากการสแกนครั้งไหน

## หลักฐาน (2026-10-11)

SQL เทียบคู่แบบไม่สนทิศ (`LEAST/GREATEST` ของ product_a_id, product_b_id):

- **31 คู่สินค้ามีสองแถว** และทั้ง 31 คู่เป็น "แถวที่คนตัดสินแล้ว + แถวคิวเดิมที่ยังค้างไม่ตรวจ"
- **0 คู่** ที่คำตอบของคนขัดกันเอง
- จาก 89 คู่ที่ผู้ใช้กดวันนี้ มี 27 คู่ที่ตรงกับแถวเดิมแต่สลับทิศ (ใช้ id เดียวกับ fixture ไม่ได้) · 38 คู่ทิศเดิมถูกอัปเดตถูกต้อง

⚠️ ตอนแรกผมนับด้วย `.select()` ตรงๆ ซึ่ง PostgREST ตัดที่ 1,000 แถว (ทั้งตาราง ~1,858) ได้ผลที่ผิด ตัวเลขข้างบนมาจาก SQL ที่ไม่มีเพดาน

## ผลกระทบ

- การสแกนไม่ได้รับผลกระทบ: `reviewed_pairs` สร้างด้วย `tuple(sorted([a, b]))` (สมมาตร) แถวที่ตรวจแล้วยังกันคู่ออกจากคิวได้
- ตัวเลข "คิวที่ค้าง" ใน DB สูงเกินจริง และสคริปต์ที่นับ/กรองจาก `similarity_matches.reviewed=false` (เช่น `apply_human_dedup_labels_r2.py` ที่ตรวจสถานะก่อนเขียน) จะเห็นแถวค้างที่จริงตัดสินแล้ว
- ข้อมูลฝึก ML ไม่ซ้ำ (ใช้เฉพาะ `reviewed=true`)

⚠️ **อันตรายที่เจอระหว่างตรวจ (คนละเรื่องกับตั๋วนี้ แต่อยู่ในไฟล์เดียวกัน):** `build_similarity_training_data.py` ลบ **ทุกแถว** ที่ `algorithm='legacy_embedding_scan'` ก่อนเขียนใหม่ ตอนนี้มี **391 แถว `reviewed=true` ที่เป็นคำตัดสินของคน** อยู่ใต้ algorithm นั้น (สคริปต์ apply_human_dedup_labels อัปเดตแถวเดิมในที่) ถ้ามีใครรันสคริปต์นี้ซ้ำ คำตัดสินของคนจะหายไปด้วย (การลบยังโดนเพดาน 1,000 แถวของ PostgREST จึงหายแค่บางส่วนและเดาไม่ได้ว่าส่วนไหน)

## ทางแก้ที่เสนอ

1. **ที่ route**: route เรียงทิศอยู่แล้ว แต่แค่เรียงไม่พอ — ต้องค้นแถวเดิมแบบสมมาตร (ทั้ง (A,B) และ (B,A)) ก่อน แล้วอัปเดตแถวที่เจอ ถ้าไม่เจอค่อย insert
2. **ที่ DB**: unique index บน `(LEAST(a,b), GREATEST(a,b))` เพื่อกันซ้ำตั้งแต่ต้นทาง ต้องเคลียร์ 31 คู่ก่อนสร้าง index
3. **เคลียร์ข้อมูลเดิม**: สำหรับ 31 คู่ ลบหรือรวมแถวค้างเข้ากับแถวที่ตรวจแล้ว (เก็บแถวที่คนตัดสิน) — สคริปต์ dry-run ก่อน ย้อนได้

ควรเขียนเทสต์ก่อน (route ไม่มีเทสต์ของ `resolve` ตอนนี้): คู่ (B,A) ที่มีแถวเดิม (A,B) ต้องอัปเดตแถวเดิม ไม่สร้างแถวใหม่
