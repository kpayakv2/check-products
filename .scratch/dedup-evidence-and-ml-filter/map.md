# แผนที่: ให้การตัดสินสินค้าซ้ำใช้หลักฐานที่ดีที่สุดที่มี และไม่ซ่อนของซ้ำจริงเงียบๆ

**Labels:** `wayfinder:map`
**Tracker:** local-markdown (ยังไม่มี issue tracker จริงในรีโปนี้)
**ตั๋วทั้งหมด:** `./issues/` — ตั๋วที่ยังเปิดอยู่คือไฟล์ที่ `Status:` ยังไม่ใช่ closed
**เปิดเมื่อ:** 2026-10-11 (จาก session ที่ผู้ใช้ตัดสินคู่สินค้า 569 คู่และรวมสินค้า 76 คู่)

## Destination

คนที่ตัดสินว่าสินค้าสองรายการซ้ำกันหรือไม่ **เห็นหลักฐานครบ** (ราคาขาย ต้นทุน บาร์โค้ด ไม่ใช่แค่ชื่อ) และ **ไม่มีตัวกรองใดในระบบซ่อนคู่ที่ซ้ำจริงไว้จากสายตาคน** โดยที่การตัดสินแต่ละครั้งไม่ทิ้งแถวซ้อนหรือแถวค้างในฐานข้อมูล

ถึงปลายทางเมื่อ: หน้าตรวจซ้ำแสดงราคา/บาร์โค้ดข้างชื่อ · คู่ที่เป็นของซ้ำจริงที่ผู้ใช้เคยยืนยันแล้วไม่ถูกซ่อน · `similarity_matches` ไม่มีคู่สินค้าที่มีสองแถวขึ้นไป

## Notes

**ที่มา — สิ่งที่วัดได้ใน session 2026-10-11 (ทุกตัวเลขตรวจกับ DB/ไฟล์จริง):**

- ไฟล์ต้นฉบับ `input/รายการสินค้าพร้อมหมวดหมู่_AI.txt` มีคอลัมน์ `ราคาขาย` · `cost` · `Barcode` (1,484 จาก 3,103 แถวมีบาร์โค้ด = 48%) แต่ `products.price/barcode/unit_name` ของสตอก **ว่างทั้งหมด** — ตอนนำเข้าไม่เคยดึงมา
- กฎ/สัญญาณที่วัดกับคำตอบของผู้ใช้ 478 คู่ในสตอก: บาร์โค้ดต่าง → คนละตัว 79% (ถ้าชื่อต่างกัน 90%) · ราคาต่าง 82% (ชื่อต่างกัน 91%) — **ไม่ถึงเกณฑ์ 95% ที่ ADR 0002 ตั้งไว้สำหรับกฎ**
- ผู้ใช้ตอบ "ตัวเดียวกัน" ให้คู่ที่ **ชื่อเหมือนกันเป๊ะ** ถึง 83 คู่ โดยในนั้น 32 คู่บาร์โค้ดต่าง และ 31 คู่ราคาต่าง (20 คู่ต่างทั้งสอง) — น่าจะเป็นคนละขนาดที่ชื่อไม่ได้บอก
- การรวมที่ผู้ใช้กดวันนี้ 76 คู่: **35 คู่บาร์โค้ดต่าง** (22 คู่ต่างทั้งราคา) รายชื่ออยู่ที่ `merged_risky.json` ใน scratchpad ของ session (ถ้าหาย สร้างใหม่ได้จาก `similarity_matches` ที่ `metadata.resolved_action='merge'` + legacy SKU)

**ข้อควรระวัง:** ห้ามเชื่อว่าบาร์โค้ดต่าง = คนละสินค้าเป็นกฎ (79%) และห้ามเชื่อว่าชื่อเหมือน = ซ้ำ (ที่ผู้ใช้เคยตัดสินด้วยชื่ออย่างเดียวผิดไปหลายคู่) ใช้เป็น **หลักฐานประกอบการตัดสินของคน** ก่อน

**ตั๋วในแผนที่นี้:** 01 หลักฐานราคา/บาร์โค้ด (grilling) · 02 ตัวกรอง ML ซ่อนของซ้ำ (grilling + bug) · 03 upsert ไวต่อทิศทาง สร้างแถวซ้อน (bug)
